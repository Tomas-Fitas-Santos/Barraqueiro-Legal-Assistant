# Improvement report — Library and Analyses

Written after a full pass over live production (<https://barraqueiro-legal.naten.ai>) on
2026-09-03, driving the real UI with Playwright as a logged-in admin. Every flow was taken
end to end: library browsing and previews, the template editors, the analysis wizard, and
**both** analysis types run on the same document (`CÓDIGO CONDUTA.pdf`, with `PPRC.pdf` as
the related document) from configuration through extraction review, legal decisions,
document generation, PDF conversion and the e-mail draft.

Two analyses were created on production for this and are still there:
`ana_oEGL9Guv-6eVal3_` (Resumo documental) and `ana_7H3k1VWs88T_7gGA` (Revisão / Atualização).

Nothing here is a plan. It is a list of what was observed, ordered by how much it costs the
person using the product. Items already fixed during the pass are marked as such and are not
open work.

## How to read the severity

- **Wrong** — the product states something untrue, or a deliverable is defective.
- **Blocking** — the user cannot do a thing the product implies they can do.
- **Friction** — the user can do it, but pays for it in clicks, scrolling or guesswork.
- **Polish** — inconsistency a careful reader notices.

## A. Analyses

### A1. The comparative matrix publishes "Pendente" on lines nobody was ever asked about — **Wrong**

`versions.ts:389` (and the same expression at `:446`) renders the decision column as:

```
item.decision === 'accepted' ? 'Aceite' : item.decision === 'rejected' ? 'Rejeitada' : 'Pendente'
```

So *every* matrix line that never required a legal decision is published as **Pendente**. In
the run above, 8 of 22 lines were gated and all 8 were decided, the gate banner cleared and
approval was allowed — yet the generated *Relatório de Revisão* still shows "Pendente" on the
ungated lines. This is a client-facing document saying that work is outstanding when it is not.

The three states are being asked to carry four meanings. An ungated line needs its own label
("—", or "Não aplicável"), distinct from a gated line still awaiting an answer.

### A2. The generated-document preview clips the letterhead logo — **Wrong (preview only)**

In the in-app preview the Barraqueiro logo is cut off: only the bottom sliver of the wordmark
survives. The `.docx` itself is correct — downloaded, converted with LibreOffice and rendered,
the logo is whole and correctly placed top-right.

So this is the preview lying about the deliverable, on the exact surface where somebody is
asked to approve that deliverable. The logo is an **inline** drawing inside the header part
(`docx-blocks.ts:171`), and the preview host is
`className="docx-host overflow-x-auto …"` (`analysis-chat-view.tsx:2121`). Because setting one
overflow axis to `auto` forces the other to compute to `auto` as well, anything `docx-preview`
places above the page box is clipped with no way to scroll to it. Worth confirming against the
header rendering in `docx-preview` before changing anything.

### A3. Rejected extraction items are a dead end — **Blocking**

The citation validators rejected 3 of 89 items on the Resumo run. The reason is shown clearly
(inexistent source, wrong page, excerpt does not match), which is good. But there is no next
step: no way to correct the citation, no override, no retry of just that item. Three
near-miss obligations simply drop out of the document, and the only recovery is to re-run the
whole extraction.

Given §10 (an unsupported field is `not_confirmed`, not silently kept), the *rejection* is
right. What is missing is the human's turn afterwards.

### A4. The legal-decision gate names a count but not a location — **Friction**

The banner says 8 items need a decision, out of 22. It does not say which. There is no filter,
no "jump to next undecided", no counter that ticks down as you go. On a 22-line matrix this is
merely annoying; on an 89-item extraction it would be unusable.

### A5. A legal decision records no justification — **Friction / audit**

Accept and Reject are single clicks with nowhere to say why. For a decision the product itself
defines as one only a lawyer may make, the audit trail is a boolean. An optional note field
would cost little and is the kind of thing that matters the one time it is asked for.

### A6. 89 items in one scrolling drawer — **Friction**

The review drawer has no grouping, filtering or search. Reviewing the Resumo extraction means
scrolling 89 cards looking for the 3 that need attention. At minimum: filter by state
(validated / rejected / needs decision), which is the same control A4 needs.

### A7. The history graph is cut off — **Friction**

`Histórico` renders a horizontal DAG that overflows the card to the right. The last node reads
"novo pedido sobr…" and there is no visible scroll affordance, so the end of the history looks
like a rendering error rather than content you can reach.

### A8. The comparative matrix is six dense columns on portrait A4 — **Friction**

Tópico / Conteúdo atual / Documento relacionado / Diferença / Alteração proposta / Decisão,
each holding a paragraph of legal prose, in a portrait page. The result is six very narrow
columns of heavily hyphenated text. Landscape orientation for that section, or splitting the
matrix into per-topic blocks rather than a table, would make the deliverable readable.

### A9. `Caminho ativo: a` leaks an internal value — **Polish**

The Detalhes tab prints the raw path letter. Either give it a human label or drop it from the
client-visible summary.

### A10. `Template nota_resumo v4` shows the raw template id — **Polish**

The wizard calls the same thing by its human name. Detalhes should too, with the version
alongside it.

### A11. Enum casing is inconsistent — **Polish**

The analysis page shows `confirmado` in lowercase where the library shows `Confirmada`. The
labels exist in `types.ts`; this surface is not using them.

### A12. `item(ns)` / `documento(s)` — **Polish**

Used throughout and inconsistently. Portuguese pluralisation here is a two-branch ternary.

### A13. Approval confirmations are native `window.confirm` — **Polish**

The PDF approval gate (correctly, per §17) asks the person to confirm they actually looked at
the pagination. It does so with a browser dialog, which is styled by the browser, not by the
product, and which cannot show what is being confirmed. A modal in the design system would
carry the same weight and look like the rest of the app.

*(Noted for the record: this also means the gate is invisible to automated checks that
auto-dismiss dialogs. That is a testing artefact, not a product defect.)*

### A14. The e-mail draft allows approval with no recipient — **Friction**

The draft shows `Para (por preencher)` and `Aprovar e descarregar (.eml)` is immediately
available. That may well be intended — the recipient is chosen in Outlook when the `.eml` is
opened, and §16 means the app never sends. If so, say so, because right now it reads like a
field somebody forgot. The editor also offers no way to add or remove attachments.

### A15. An empty `/analyses` renders nothing at all — **Friction**

No empty state, no explanation, no call to action. A first-time user landing there sees a blank
page.

## B. Library

### B1. Folder navigation is not in the URL — **Blocking**

`?path=…` is ignored. A folder cannot be deep-linked, bookmarked, sent to a colleague, or
reached with the browser Back button. Every visit starts at the root and clicks down. This is
the single largest usability gap in the Library.

### B2. The type of a file is rendered in the wrong column — **Wrong**

Inside `2. Templates/Resumo documental`, every file shows `—` under **Tipo**, while the word
**Template** — which is the document *kind* — appears under **Estado**. Folders, meanwhile,
correctly show `Pasta` under Tipo.

So the one field the agreed layout deliberately keeps in the list because it identifies what a
row is, is blank for files, and the column meant for state is showing a type instead. Whatever
the cause, the two columns currently disagree about what they hold.

### B3. A stray duplicate template — **Wrong (data)**

`2. Templates/Revisão e Atualização` holds `email-revisao 1.eml` beside `email-revisao.eml`
(`doc_RDFFQDWcVjimD5ux`). It looks like a name collision from a republish. Worth finding out
how it got there before deleting it, since the mechanism will produce another one.

### B4. Metadata tab: always-editable fields with no Save — **Friction**

Fields on the Metadados tab look editable at all times and there is no visible save control, so
it is not clear whether typing changes anything. Long values (Subtemas) overflow or truncate,
and dates are shown as raw ISO strings rather than pt-PT.

### B5. Wizard step 3 does not use what the system already knows — **Friction**

`Documentos relacionados` lists every document in the library, flat, with no indication of
which pairs already have a stored relation nor at what confidence. The detail page for
`CÓDIGO CONDUTA.pdf` knows perfectly well that `PPRC.pdf` is a high-confidence relation — the
wizard, one click away, does not show it. Surfacing known relations first (with their
confidence band) would turn a scan of the whole library into a confirmation.

This also has a data consequence worth checking separately: documents picked in the wizard are
inserted with `relation_type='selecionado_no_assistente'` and **no `relation_id`**
(`analyses.ts:~393`), so a wizard pick and a known relation are two different rows describing
the same pair.

### B6. Wizard step 4 has no selected state — **Friction**

The single `.docx` template card looks selectable but shows no selected indicator, so there is
no feedback that a choice was registered. Card width also differs between steps 3 and 4, which
makes the wizard feel like two different screens.

### B7. Wizard step 5 summary is thin — **Friction**

The final step recaps neither the related documents nor the template. It is the last chance to
catch a wrong pick before a long run starts.

### B8. Fixed during this pass

- **The row menu was clipped** by the scrolling list panel, putting Descarregar / Reprocessar /
  Eliminar out of reach on the last rows of a folder. Fixed in `3bc4bab` by anchoring the menu
  to the viewport.
- **Templates had no edit affordance in the list.** Fixed in `3bc4bab`; a template row now
  carries the id of the editor it opens, resolved by name across all three registries.

## C. What is working, and should not be traded away

Worth writing down, because a list of defects gives a false impression.

- The grounding contract holds visibly. The Resumo run reported *"Removi 2 marcador(es) de
  referência inválido(s) do texto — só cito fontes verificadas"* and the citation validators
  rejected 3 of 89 items on their own. The product refuses to cite what it cannot support,
  and says so in plain Portuguese.
- The confirmation gates are real gates. The legal-decision gate genuinely blocked approval
  until all 8 decisions were made; the PDF gate genuinely asks a person to attest to the
  pagination.
- The full chain works on production, unattended: extraction → review → generation → PDF (16
  pages, 354 KB, via Graph) → `.eml` draft with the approved PDF attached, with §16 intact —
  the app prepares an e-mail and never sends one.
- Dark mode is correct, including the deliberate choice to keep the document preview on a white
  page. A document is a document.
- The generated `.docx` is genuinely well-formed: correct letterhead, correct styles, numbered
  references resolving to real excerpts.

## D. Suggested order

If these are worked, the order that buys the most per unit of effort:

1. **A1** — a client-facing document is stating something untrue. Cheapest fix on the list.
2. **B1** — folder path in the URL. Affects every Library session.
3. **A2** — the preview must agree with the document it is previewing.
4. **A3 + A4 + A6** — one filter/navigation control on the review drawer covers all three, and
   A3 needs a decision about what recovery should mean before it can be built.
5. **B2, A9, A10, A11, A12, A15** — small, independent, all safe to bundle.
6. **B5** — needs the `relation_id` question answered first.
7. **A5, A8, A13, A14, B4, B6, B7** — real improvements, none of them urgent.

## E. Loose ends from this pass

- The two test analyses above are still on production, along with their generated documents,
  PDFs and accepted legal decisions. They should be removed once this report has been read.
- `email-revisao 1.eml` (B3) is unexplained.
